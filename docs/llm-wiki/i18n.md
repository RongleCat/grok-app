# Internationalization (i18n)

**Rule:** User-visible UI strings must not be hard-coded. Use `t(locale, key)` / `createT(locale)`.

**Catalog fallback is English (`en`).** This file is the source of truth for the shipped ids. Thirteen locales ship: `de`, `en`, `es`, `fr`, `id`, `it`, `ja`, `ko`, `pt-BR`, `ru`, `uk`, `zh` (Simplified Chinese), `zh-TW` (Traditional Chinese). A locale ships only when it is a language we are willing to support in Settings — the picker in `GeneralSection.tsx` must never offer an id that is not listed here. The Chinese catalogs are complete translations. Every other non-English catalog is **English-backed with explicit overrides** (`{...en, ...overrides}`), so a newly added upstream key can never render blank while translation coverage grows incrementally. `messages.test.ts` enforces key parity, non-empty values, translated always-visible chrome, and placeholder survival across every locale.

**User preference default is `system`** (follow OS UI language). A Japanese, German, Korean, … Windows / macOS / Linux install must open in that language without a Settings visit. Unknown OS languages still fall back to English.

## Adding or changing copy

1. Add the key to the **`en` catalog** first (dot keys: `area.action`).
2. **Same PR:** fill `zh` and `zh-TW` with complete translations; add the override for any other locale whose translated surface the copy belongs to.
3. In components: `const tr = useMemo(() => createT(locale), [locale]);` then `tr("sidebar.settings")`.
4. Variables: template `{name}`, call `tr("project.trustFirst", { name: proj.name })`.
5. Do **not** spread `locale === "zh" ? "…" : "…"`; replace leftovers with keys.
6. Product / model names (`Grok 4.5`, `Agent`) may stay English; descriptive UI should be localized where that locale has coverage.
7. Language switch writes `settings.locale` and updates UI immediately.
8. Prefer `createT(locale)` over partial label maps (missing keys show raw `settings.foo`).
9. Keep frontend locale parsing and all native locale-dependent matches in sync whenever a locale is added.
10. Add regression coverage for native locale-specific branches (tray/menu/session-title helpers) so exhaustive Rust matches and locale cleanup stay cross-platform safe.

## Adding a locale

0. Confirm it is a language we intend to support in the product UI, then update the shipped list at the top of this file **in the same PR**. This file and the Settings picker must agree with `LOCALES`; the catalog test asserts the roster.
1. Append the id to `LOCALES` in `src/i18n/messages/index.ts` and create `src/i18n/messages/<id>/index.ts` as `{ ...en, ...overrides }`. `Locale`, `isLocale` and every parity test derive from `LOCALES`.
2. Add the endonym to the picker in `GeneralSection.tsx`.
3. Add an `INTL_TAGS` entry in `src/i18n/index.ts` — never let a raw catalog id reach `Intl`.
4. Add a `BOOT_I18N` entry in `index.html`. The splash paints before React loads, so it carries its own copy of the welcome line, the detecting line and the `<html lang>` value. A missing entry silently falls back to English on first paint.
5. Mirror the id in `src-tauri/src/tray_i18n.rs`: `Locale` variant, `from_lang_tag` arm, `as_tag`, `english_name`, a `TrayStrings` const, the `strings()` arm, and a `windows_langid_to_tag` entry if Windows has a LANGID for it.
6. Add the three `remote_im/i18n.rs` strings, and add the id to `tray_i18n::ALL` — placeholder-title detection walks it, so a locale missing there stops auto-titling for its users.
7. Extend the alias table (`LOCALE_ALIASES` / the `from_lang_tag` match) if the OS emits a regional or legacy tag that must fold into the new catalog.

## Defaults

| Layer | Default |
|-------|---------|
| `AppSettings.locale` | `"system"` (follow OS; users may lock any catalog id) |
| `resolveLocale(undefined)` | follow system (unknown OS → `en`) |
| `resolveLocale("system")` | maps Host OS tag / `navigator.language` → a catalog id |
| Tray unknown locale | English |
| Settings language dropdown | **System** first, then one endonym per shipped locale — nothing else |
| Compact counts (`formatTokenCount` / `formatLocaleCount`) | myriad units for `zh` / `zh-TW` / `ja` / `ko`; K/M/B everywhere else |

## Formatting

Never fork a format on `locale === "zh"`. Two helpers cover it:

- **`intlLocale(locale)`** → the BCP-47 tag for every `Intl.*` constructor and `toLocaleString`. It exists because catalog ids are not always safe ICU input: `zh` must become `zh-CN`, not the generic macrolanguage. Every shipped locale currently maps to its own regional tag; a future catalog whose language carries thin CLDR data borrows a neighbouring tag here instead of reaching a formatter raw. `htmlLangForLocale` must not follow such a borrow — a screen reader has to be told the language actually on screen.
- **`formatListTimestamp(iso, locale)`** (`src/lib/formatDateTime.ts`) → absolute timestamps in history and audit lists. Never call `toLocaleString(undefined, …)`: `undefined` is the WebView language, not the language the user picked. Clocks are 24-hour everywhere (`hour12: false`), matching `formatMessageTime` and the tray.
- **`isTightScript(locale)`** → true for Chinese and Japanese, whose typography sets a unit or weekday against its number with no space (`火15:23`, `9時間36分`). **Korean is not tight** — its orthography spaces words (`화 15:23`).

Counts group by myriad (10⁴) for `zh` / `zh-TW` / `ja` / `ko` via `myriadUnitsFor` in `src/lib/formatCompactCount.ts` — 万/萬/만 and 亿/億/억 differ per locale, so never hard-code 万.

Durations use CLDR narrow units through `Intl.NumberFormat({ style: "unit" })`. Japanese is the one documented override in `heatmapStats.ts`: CLDR's Japanese *narrow* units are the Latin `h`/`m`/`s`, and its *short* units insert a space (`9 時間`), so Japanese carries its own suffixes.

## Follow system

- Preference value stored in `settings.locale` is the string `"system"` (not the resolved catalog id).
- Frontend: `resolveLocaleFromSystem(langTag)` (pure) + Host `__GROK_BOOT_OS_LANG__` + `navigator.languages` + `languagechange` while preference is system.
- Tray / boot: `Locale::from_system` prefers macOS `AppleLanguages` / Windows UI language/locale APIs, then POSIX `LANG` / `LC_*` (ignores `C` / `POSIX`).
- Regional aliases resolve to their catalog: `ru_RU.UTF-8` → `ru`, `de-AT` → `de`, `es-419` → `es`, `fr-CA` → `fr`, `ja_JP.UTF-8` → `ja`.
- All Portuguese folds into `pt-BR` (`pt`, `pt-PT`, `pt-BR`); the retired `in` code folds into `id`.
- An OS language with no shipped catalog falls through to `en` on both sides — it must never resolve to an id that is not in `LOCALES`.
- One-shot: persisted factory `"en"` → `"system"` (`localeFollowSystemMigrated`). Explicit catalog ids and `"system"` stay.

## Translation quality

- **English:** primary product language for open source; clear, concise desktop tone.
- **Chinese:** complete sentences, consistent product tone.
- **Other locales:** natural desktop terminology, concise labels, no literal machine-style translation. Keep placeholders (`{name}`, `{n}`, `{path}`, …) unchanged and preserve product/CLI identifiers.
- **Scope:** only real OS UI languages ship. Novelty or liturgical locales are out of scope — the picker is a support commitment, not a showcase.
